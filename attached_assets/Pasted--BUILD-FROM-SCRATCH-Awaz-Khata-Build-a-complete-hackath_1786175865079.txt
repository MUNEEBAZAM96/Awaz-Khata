# BUILD FROM SCRATCH — آواز کھاتہ (Awaz Khata)

Build a complete hackathon-ready application from scratch called:

# آواز کھاتہ — Awaz Khata

### Tagline

**اپنے پیسوں کا حساب، بس بول کر۔**

English:
**Your personal finances, just by speaking.**

This is a **voice-first personal finance assistant designed for Pakistani users**.

The entire primary interaction should happen through **voice**.

The user should be able to speak naturally in:

* Urdu
* Roman Urdu
* English
* Urdu + English mixed speech

The app should understand what the user said, record the financial information, calculate financial summaries, and answer questions back using **Urdu voice**.

This application is being built specifically for the:

**Uplift AI × Replit Voice AI Hackathon**

The most important goal is:

> **SPEAK → UNDERSTAND → SAVE/CALCULATE → SPEAK BACK**

Do NOT build a generic expense tracker.

Do NOT build a complicated banking application.

Do NOT over-engineer the product.

Build a small, extremely reliable voice-first MVP that works beautifully during a live hackathon demonstration.

## Frontend

Use:

* React Native
* Expo
* Expo Router
* TypeScript
* NativeWind
* Axios
* Expo audio recording/playback APIs compatible with the installed Expo SDK

The frontend must be a proper Expo Router application.

Do NOT use another navigation library.

---

# 2. VOICE + AI STACK

Use **Uplift AI** as the core voice platform.

Use the official Uplift AI SDK available for the project.

Use Uplift AI for:

### Speech-to-Text

User speaks Urdu/Roman Urdu.

Audio → Uplift AI → text

### Text-to-Speech

Financial response → Uplift AI → Urdu audio

Use Uplift AI's available voice capabilities and choose/configure a clear, natural Urdu voice.

Keep Uplift integration inside the backend.

The React Native frontend must NEVER contain the Uplift API key.

---

# 3. LLM

Use **Groq** as the LLM provider.

Use Groq's fast inference to understand the transcription and convert natural language into structured financial intents.

The LLM should NOT perform actual financial calculations.

The LLM only determines:

> What did the user mean?

The backend finance engine determines:

> What is actually in the user's financial data?

This separation is extremely important.

# 9. FOUR FINANCIAL TRANSACTION TYPES

Only support these four types for the MVP:

```text
expense
income
given
received
```

### expense

Money the user spent.

Example:

> "میں نے آج 800 روپے پٹرول پر خرچ کیے۔"

### income

Money received as income.

Example:

> "آج مجھے دس ہزار روپے ملے۔"

### given

Money the user gave to another person.

Example:

> "میں نے علی کو دو ہزار روپے دیے۔"

### received

Money received back from another person.

Example:

> "علی نے پانچ سو روپے واپس کیے۔"

# 10. VOICE PIPELINE

The most important flow in the entire application:

```text
User speaks
    ↓
Expo records audio
    ↓
Frontend uploads audio to Backend
    ↓
Backend → Uplift AI STT
    ↓
Urdu transcription
    ↓
Backend → Groq
    ↓
Structured JSON intent
    ↓
Backend validates intent
    ↓
Finance engine saves/calculates
    ↓
Backend creates Urdu response
    ↓
Backend → Uplift AI TTS
    ↓
Audio returned
    ↓
Expo plays audio
```

The user should experience this as one simple conversation.

# 11. SPEECH-TO-TEXT

Create:

```http
POST /api/voice/transcribe
```

Accept:

```text
multipart/form-data
audio=<recording>
```

Use multer.

Send the audio to Uplift AI Speech-to-Text through the official SDK.

Wrap the call in proper error handling.

Return:

```json
{
  "text": "میں نے علی کو دو ہزار روپے دیے"
}
```

If transcription fails:

```json
{
  "error": "آواز سمجھ نہیں آئی، دوبارہ کوشش کریں۔"
}
```

Do not expose SDK errors directly to the user.

Log useful technical errors on the backend.

# 13. GROQ SYSTEM PROMPT

Use a strict system prompt similar to:

```text
You are the financial intent extraction engine for Awaz Khata,
a Pakistani voice-first personal finance assistant.

The user speaks naturally in Urdu, Roman Urdu, English,
or mixed Urdu and English.

Your job is ONLY to understand the user's financial intent
and return valid JSON.

Never return markdown.
Never return explanations.
Never return code fences.
Return JSON only.

SUPPORTED TRANSACTION TYPES:

expense:
Money the user spends.

income:
Money the user receives as income.

given:
Money the user gives to another person.

received:
Money the user receives back from another person.

TRANSACTION FORMAT:

{
  "mode": "transaction",
  "type": "expense | income | given | received",
  "amount": number,
  "person": "string or null",
  "category": "string or null",
  "description": "string or null"
}

SUPPORTED QUERIES:

{
  "mode": "query",
  "query_type": "total_expenses | total_income | person_given | person_received | person_balance | today_summary | monthly_summary | category_summary | recent_transactions",
  "period": "today | this_week | this_month | all_time | null",
  "person": "string or null",
  "category": "string or null"
}

RULES:

1. Never invent an amount.
2. Never invent a person.
3. Convert Urdu number words into numbers.
4. Understand Pakistani Urdu expressions.
5. Understand Roman Urdu.
6. Understand English.
7. Understand mixed language.
8. Preserve person names.
9. Do not calculate financial balances.
10. The backend will perform calculations.
11. If the request is ambiguous, return:

{
  "mode": "unknown"
}

Examples:

"میں نے 800 روپے پٹرول پر خرچ کیے"

→ transaction / expense / 800 / transport

"میں نے علی کو دو ہزار روپے دیے"

→ transaction / given / 2000 / Ali

"علی نے پانچ سو روپے واپس کیے"

→ transaction / received / 500 / Ali

"میں نے آج کتنے پیسے خرچ کیے؟"

→ query / total_expenses / today

"علی کے کتنے پیسے باقی ہیں؟"

→ query / person_balance / Ali
```

Use structured JSON output if the selected Groq model/API supports it.

Still validate the response server-side.

# 39. FINAL PRODUCT PHILOSOPHY

Do NOT think:

> "I am building an expense tracker with voice input."

Think:

> **"I am building a Pakistani voice assistant that remembers and manages my money."**

The user shouldn't need to navigate menus.

They shouldn't need to manually select categories.

They shouldn't need to type transactions.

They simply speak.

Examples:
